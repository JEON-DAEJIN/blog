## 수업내용 요약

### N033. 나만의 에이전트 하네스 만들기
- **하네스(Harness)란 무엇인가**: 모델의 요청을 실제 실행과 연결하고 그 결과를 다시 전달하는 프로그램. 핵심은 "모델은 무엇을 할지 판단하고, 하네스는 어디까지 실행할 수 있는지 통제한다"는 역할 분리다. Claude Code·OpenCode 같은 개발 AI는 이 하네스를 설계·구현하도록 돕는 협업 도구일 뿐, 이번 수업의 진짜 제출물은 직접 완성한 하네스다.
- **미완성 PRD와 설계 대화**: 완성된 코드를 바로 실행하지 않고, 미완성 PRD(제품 요구사항 문서)를 AI와의 대화로 한 항목씩 채운다. 미결정 항목은 결정 ID(D01~D09)로 추적하고 OPEN(미결정)/CHOSEN(합의 완료)/DEFERRED(지금은 미루기로 결정, 필요 없다는 뜻 아님) 세 상태로 관리한다. "지침"(하지 마세요, 라고 알려주는 것)과 "강제 검사"(조건 미충족 시 실행 자체를 코드로 차단하는 것)는 전혀 다른 수준의 안전장치라는 구분도 여기서 나온다.
- **플랫폼·언어·기능 범위**: 화면(UI), 하네스 실행 위치, 모델 실행 위치는 서로 다른 결정이며, 특별한 이유가 없으면 로컬 Python CLI를 첫 선택으로 권장한다. 기능은 한 번에 다 만들지 않고 "작더라도 여러 층을 처음부터 끝까지 관통하는" 수직 구현으로 먼저 완성한다. 그리고 "실행 성공 ≠ 작업 성공" — 에러 없이 끝까지 돌았다는 것과 사용자가 원한 결과를 실제로 얻었다는 것은 다르다.
- **완료 조건을 구현 전에 정의**: "어떤 상황에서 무엇을 관찰하면 성공인가"를 코드를 짜기 전에 `ACCEPTANCE.md`(A01~A12)로 먼저 정리한다. 영수증 계산 예시(장소비를 인원수만큼 중복 계산하는 결함)처럼, 완료 조건을 정확히 적어두지 않으면 결함을 테스트만으로는 눈치채기 어렵다.
- **실행 가능한 Python 하네스(harness_lab)**: Agent(전체 흐름 조율)·Provider(모델 연결)·Tools/Backend(실제 실행)로 구성된 실제 코드를 직접 돌려봤다. `uv run run.py`로 파일 읽기·영수증 버그 수정 작업을 클라우드 모델(OpenAI)과 로컬 모델(Ollama) 양쪽으로 실행.
- **Terminal-Bench Pro 로컬 10문항 평가**: 원본 벤치마크에서 easy 2·medium 4·hard 4 총 10문제를 Docker 없이 로컬로 이식한 버전으로 직접 만든 하네스의 실력을 측정한다. 점수를 볼 때 "분모를 몰래 줄이는" 함정(오류를 빼고 계산)을 주의해야 하고, baseline과 improved를 비교할 때는 한 번에 하나의 변경 가설만 세워야 한다.
- **결과 해석의 절제**: 같은 10문제로 반복 개선했다면 그건 "개발용 평가 집합"에 익숙해진 결과일 수 있으므로, "우리 하네스는 모든 작업에서 뛰어나다"로 확대 해석하면 안 된다. 최종 제출물은 구현체·baseline/improved 실행 기록·두 결과 비교 분석 세 가지가 하나로 묶여야 한다.

## 기술 질문과 답변
**질문**: 오늘 배운 개념 중 "지침(instruction)"과 "강제 검사(hard constraint)"의 차이, 그리고 "실행 성공"과 "작업 성공"의 차이를 직접 설명해 주시겠어요? (실습해보신 것과 연결해서 답해주세요 — 예: 오늘 실습이나 벤치마크를 돌리면서 이 두 구분이 왜 중요하다고 느끼셨는지)

**답변**: 지침은 단순한 가이드 라인, 강제검사는 프로그램이 조건을 검사해서 통과하지 않으면 다음 단계로 넘어가지 못하게 하는 장치. 실행성공은 과정에 대한 판단, 작업 성공은 결과에 대한 판단.

## 에세이 질문과 답변
**질문**: "무거운 작업은 노트북이 이겨내지 못해서, Colab을 돌려도 시간이 오래 걸리고 결국 기다리는 수밖에 없었다"고 하셨는데요 — 28년 경력 중에도 이렇게 "내 통제 밖의 것을 그냥 기다려야만 했던" 순간이 있으셨나요? 그때와 오늘의 기다림은 어떻게 다르게(혹은 비슷하게) 느껴지셨는지 궁금합니다. (그날 있었던 구체적인 장면과 연결해서 답해주세요)

**답변**: 애플에 앱을 올릴 때 마냥 기다리던 순간이 기억나네, 우리가 할 도리는 다 했는데 애플의 불친절한 승인거부에 다시 올리고 또 기다리는 작업을 반복하던 때가 생각나. 그때보다는 확실히 시간이 걸린다는 것 뿐 해결가능한 것을 기다리는 것이라 초조하지는 않아. 실패하더라도 수정 가능한 것도 아니.

## 클로의 피드백
**좋은 점**
- 기술 답변에서 "지침=가이드라인" / "강제검사=통과 조건을 검사해서 다음 단계로 못 넘어가게 막는 장치"라는 대응이, 강의 원문("지침 → 하지 마세요 → 행동 방향을 알려 줌" / "강제 검사 → 조건 미충족 시 실행 자체를 차단")과 정확히 겹친다. "실행 성공=과정에 대한 판단, 작업 성공=결과에 대한 판단"이라는 압축도, 원문의 "에러 없이 끝까지 실행됐다는 것"과 "사용자가 원한 작업을 실제로 해냈다는 것"을 자기 언어로 정확히 응축한 것이다.
- 에세이 답변에서 앱스토어 심사 사례를 끌어온 것이 예리하다. "해결 가능한 것을 기다리는 것이라 초조하지 않다"는 문장은, 사실 오늘 배운 "완료 조건을 미리 정의한다"는 개념과 은근히 맞닿아 있다 — 무엇을 관찰하면 끝나는지 알고 기다리는 것과, 그걸 모른 채 막연히 기다리는 것의 차이를 스스로 짚어낸 셈이다.

**개선점**
- `[책에 실을 때 보완하면 좋을 부분]` 기술 답변에 오늘의 실제 실습 장면 하나를 붙이면 더 좋겠다. 예를 들어 "Colab 대기 시간이 길어도 이건 강제 검사가 아니라 그냥 자원 제약이니 지침 수준에서 참고 기다리면 된다"처럼, 오늘 겪은 어려움과 두 개념을 직접 연결하는 문장이 있으면 이론과 경험이 한 번 더 이어진다.
- `[에세이 보강 여지]` "실패하더라도 수정 가능한 것도 아니"라는 문장은 앞뒤 맥락이 조금 끊겨 보인다. 애플 심사와 오늘의 기다림 중 어느 쪽이 "수정 불가능"에 가까운지 한 문장만 더 붙이면, 두 기다림의 차이가 훨씬 선명해질 것 같다.
