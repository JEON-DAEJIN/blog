## 오늘 배운 내용

- 오늘은 오후 수업에만 참여했다.
- AI Service in Production을 배웠다.

## 수업내용 요약 (N046 · AI 서비스 인 프로덕션)

### 1. 왜 "로컬에서 돌아간다"로는 부족한가

- 로컬 실행은 내 방에서만 운영하는 가게이고, 클라우드 배포는 인터넷에 문을 연 가게다. 컴퓨터를 끄면 로컬 서비스도 멈춘다.
- AI 서비스는 LLM 키를 숨겨야 하고, 메시지 하나에 LLM을 여러 번 부르며, 호출마다 비용이 든다.
- 배포가 필요한 이유는 접근성, 보안, 운영 효율이다.

### 2. Vercel과 Cloud Run

- 둘 다 서버리스(요청이 많으면 늘고 없으면 0개로 줄어듦)이고, 차이는 런타임과 의존성을 누가 정하느냐다.
- Vercel은 준비된 주방을 쓰는 식당, Cloud Run은 도구를 직접 챙겨 컨테이너 상자에 담아 올리는 식당이다.

### 3. Google Cloud 준비

- 구조는 Google 계정 → 결제 계정 → 프로젝트 → API 사용 설정과 리전 순이다.
- 서비스 6종: Cloud Run(실행), Cloud Build(조립), Artifact Registry(창고), Secret Manager(금고), IAM(출입 권한), Cloud Logging(업무 일지).
- 명령에는 프로젝트 이름이 아니라 프로젝트 ID를 쓴다.

### 4. 배포 명령 한 줄 뒤의 5단계

- 빌드 → 이미지 저장 → 리비전 → 인스턴스 → 서비스 URL이 차례로 진행된다.
- 리비전은 이미지와 설정을 기록한 배포 버전이고, 인스턴스는 그 레시피로 요리하는 주방이다.
- 각 단계를 콘솔의 빌드 기록, 이미지 저장소, 리비전 탭, 측정항목, 로그에서 하나씩 찾아볼 수 있다.

### 5. 리비전, 롤백, 트래픽 분할

- 롤백은 코드를 지우는 것이 아니라 요청이 가는 곳을 바꾸는 것이다. 고정해 두면 새 배포가 트래픽을 못 받으니 최신으로 돌려놓아야 한다.
- 트래픽을 50:50으로 나누는 카나리 배포로 새 버전을 일부에게만 먼저 보여 줄 수 있다.

### 6~7. 로컬 실행, .env, Secret Manager

- `.env`는 `.gitignore`와 `.gcloudignore`로 저장소와 배포에 올라가지 않으므로, 키 없이 배포하면 서버에 키가 없다.
- 첫 배포의 터미널 메시지는 포트를 말했지만 진짜 원인은 로그의 키 누락이었다. 터미널 메시지는 결과이고 로그가 원인이다.
- 키는 Secret Manager에 두고 서비스에는 이름으로만 연결한다. 환경변수에 값을 직접 넣으면 리비전 설정에 그대로 남는다.

### 8. 코딩 에이전트에게 맡길 때

- 최소 권한 원칙, 에이전트 안전 3요소(변경 범위·변경 결과·검증 방법), "로그를 근거로 설명해 줘, 아직 고치지 마"라는 요청 방식.

## 클로의 피드백

### 기술 질문 답변

- **좋은 점**: 핵심을 정확히 짚었다. 오류의 정체가 "연결 불가"가 아니라 "키 없음"이었고, 로그를 열어 보지 않았다면 알 수 없었다는 판단은 오늘 강의의 결론(터미널은 결과, 로그는 원인)과 같다.
- **개선점**: 로그에서 실제로 본 줄(`LLM_API_KEY 환경변수가 없어 앱을 시작하지 않습니다.`)과 터미널 메시지(포트)를 나란히 적으면 책에 실을 때 훨씬 생생해진다. [에이전트에게 시킬 때는 "로그를 근거로 원인을 설명하고 아직 고치지 마"라고 요청한다는 점도 한 줄 보태면 좋다.]

### 에세이 질문 답변

- **좋은 점**: 받은 도움을 "동료가 자기 프로젝트를 보여 주며 가르쳐 줬다"는 구체적인 장면으로 적었다. 질문을 두려워하지 않는 수업 분위기가 실제 결과물(영상)로 이어진 사례다.
- **개선점**: 질문의 둘째 부분, 내일 팀원에게 먼저 도움이 되는 구체적인 행동이 아직 비어 있다. [예를 들어 오늘 만든 영상 소스를 동료에게 공유하거나, 로그를 읽는 순서를 알려 주는 식으로 한 가지를 정해 적어 보자.]
