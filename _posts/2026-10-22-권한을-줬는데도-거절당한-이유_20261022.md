## 수업내용 요약 (N048 · GitHub Actions로 자동 배포하기)

### 1. CI와 CD, 그리고 오늘 만드는 것

- CI는 작은 단위로 자주 합치고 자동 검사하는 것, CD는 그 결과를 배포까지 자동화하는 것 — 오늘 만든 것은 사람 승인 없이 머지 즉시 나가는 "지속적 배포(Continuous Deployment)"다.
- 워크플로 파일 하나에 트리거(`on`)·러너(`runs-on`)·단계(`steps`)·권한(`permissions`)이 전부 들어 있는 구조를 익혔다.
- 액션 버전(`@v3` 등)은 템플릿에 적힌 그대로 쓰고 임의로 바꾸지 않는다는 원칙을 확인했다.

### 2. 브랜치·PR·머지 연습

- README PR, 연습용 `hello.yml` PR로 브랜치→커밋→푸시→PR→머지 흐름을 다시 익혔다.
- 일부러 `exit 1`로 실패시켜 뒤 단계가 건너뛰어지는 것과, `git revert`로 되돌리는 법을 직접 확인했다.
- PR 화면의 "상태 체크"는 결과만 보여줄 뿐 머지를 막지는 않는다는 것도 실제로 확인했다.

### 3. 키 파일 없이 권한 주기 — WIF

- Workload Identity Federation으로, GitHub이 서명한 토큰을 "내 저장소에서 온 것만" 받는 공급자 조건과, 그 신원이 쓸 수 있는 서비스 계정을 정하는 권한 연결 — 두 번의 검사를 거치게 설계했다.
- 런타임 계정과 배포 계정을 역할별로 나눠 각각 필요한 권한만 주는 최소 권한 원칙을 실습했다.

### 4. 실습 중 직접 부딪힌 함정

- 배포 계정에게 빌드 계정의 역할을 "쓸 권한"만 줬을 뿐, 빌드 계정 쪽에서 "너를 믿는다"는 신뢰 관계를 열어주지 않아 첫 배포가 실패했다.
- 강의 문서에도 안 나와 있던 부분이라, 로그를 직접 읽고 원인을 찾아 고쳤다.

### 5. 사고 2건 — 배포 실패 vs 결과 오류

- 환경변수 이름을 잘못 바꾼 사고: 배포 자체가 실패해 이전 버전이 계속 서비스됐고, 사용자는 전혀 몰랐다.
- 시간대 정보를 뺀 사고: 배포는 성공했지만 "내일 아침 8시" 약속이 실제로는 17시로 저장되는, 결과가 틀린 채 그대로 나간 사고 — "배포 성공 ≠ 결과가 맞다"는 것을 몸으로 확인했다.
- 둘 다 `git revert`로 만든 되돌림 PR을 머지하는 것만으로 복구됐다.

### 6. 감사 로그로 "누가, 어디서"

- Google Cloud 감사 로그를 열어 사람이 수동 배포했을 때(내 계정만 남음)와 오늘 자동 배포(배포 서비스 계정 + 저장소·브랜치 정보까지 남음)를 직접 비교했다.
- 연습용 저장소를 하나 만들어 똑같이 흉내 내봤더니 "속성 조건에 의해 거절됨"으로 정확히 막히는 것도 확인했다.

### 7. 과제로 마무리

- 화면에 배포된 커밋을 보여주는 작은 배지를 추가해 자동 배포 파이프라인을 한 번 더 써 봤다.
- 오늘 과정을 58초짜리 모션 영상으로 요약해 Notion에 올렸다.

## 기술 질문과 답변

**질문**: 오늘 실습에서 "배포 계정이 빌드 계정을 대신 행동할 권한이 없다"는 오류를 직접 만나셨죠. 이 문제가 왜 생겼는지, 그리고 "어떤 계정에 역할을 주는 것"과 "그 역할을 실제로 쓸 권한을 주는 것"이 왜 서로 다른 건지 본인 말로 설명해 주세요.

**답변**: 오늘 실습 중 겪은 오류는 '자격(Role)을 가지고 있는 것'과 '그 자격을 다른 주체에게 위임(Assume)하는 것'이 별개의 설정이기 때문에 발생했습니다. 마치 회사에서 특정 부서의 직함(역할)을 부여받았더라도, 해당 업무를 처리할 때 내 명의가 아닌 타인의 명의나 공용 계정으로 대신 로그인해서 실행하려면 별도의 위임장이나 승인(Trust Policy)이 필요한 것과 같습니다. 즉, 배포 계정에 빌드 계정의 역할을 사용할 권한(Role)을 부여했다고 해서 끝이 아니라, 빌드 계정 측에서도 "이 배포 계정이 나를 대신해서 행동하는 것을 허용한다"는 신뢰 관계(Trust Relationship)가 반드시 함께 설정되어야만 정상적으로 권한을 위임받아 실행할 수 있다는 것을 이번 실습을 통해 확실히 이해하게 되었습니다.

## 에세이 질문과 답변

**질문**: 오늘 다른 크루들의 프로젝트를 들여다보다가 본인 프로젝트 후보를 몇 개 발견하셨다고 하셨는데요 — 구체적으로 무엇을 보다가 어떤 아이디어가 떠올랐나요? 그리고 28년간 신규사업을 기획하시면서도 "남이 뭘 하는지 관찰하는 것"이 실제 사업 아이디어로 이어졌던 경험이 있다면, 오늘 느낀 것과 어떻게 겹치는지도 함께 적어 주세요.

**답변**: 아주 간단히 실생활에 쓰일 수 있으면서도 우리가 배운 학습 내용의 keys를 활용할 수 있는 분야였어.

## 클로의 피드백

### 기술 질문 답변

- **좋은 점**: 핵심을 정확히 짚었다. "역할(Role)을 가진 것"과 "그 역할을 위임받아 대신 행동하는 것(Assume)"을 분리해서 설명한 것은, 오늘 직접 고친 문제(배포 계정의 `iam.serviceAccountUser` 권한 누락)의 본질 그 자체다. 특히 "타인 명의로 로그인하려면 별도 위임장이 필요하다"는 회사 비유는 신뢰 관계(Trust Relationship)라는 추상적 개념을 정확하게 체화한 설명이다.
- **개선점**: GCP의 실제 메커니즘 이름(배포 계정에게 빌드 계정 위에 `roles/iam.serviceAccountUser`를 부여하는 것 자체가 이 "위임장"의 실체다)을 한 문장만 더 붙이면, 오늘의 비유와 실제 명령이 바로 연결돼 책에 실을 때 더 또렷해진다.

### 에세이 질문 답변

- **좋은 점**: 오늘 배운 핵심(키 관리, 권한 위임 같은 "안전하게 연결하는 법")을 실생활 서비스 아이디어의 재료로 보려는 시도 자체가 좋다.
- **개선점**: 질문의 구체적인 부분 — 어떤 크루의 어떤 프로젝트를 보다가 아이디어가 떠올랐는지, 그리고 28년 경력에서 "관찰이 실제 사업 아이디어로 이어졌던" 구체적 장면 — 이 아직 비어 있다. [주말에 프로젝트 후보를 추릴 때, 오늘 본 장면들을 먼저 한 줄씩 메모해 두면 다음에 훨씬 풍부하게 쓸 수 있다.]
