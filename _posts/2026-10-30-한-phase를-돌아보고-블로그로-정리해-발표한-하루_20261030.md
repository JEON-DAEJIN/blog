## 오늘 배운 내용

- 이번 phase에서 배운 것을 정리하고, 그것을 블로그로 올려 보았다.
- 자기 블로그를 공개하고 서로 발표해 보았다.
- 나는 9부 「서비스화·배포·운영」(N045~N053) 아홉 강의를 정리 문서로 묶고, 그것을 바탕으로 블로그 특별편 「AI 서비스를 세상에 내놓으며 깨진 9가지 착각」을 써서 올렸다. 글 앞에 아홉 강의 흐름 그림을 넣고, 같은 그림으로 30초 모션 영상도 만들었다. 영상과 GIF가 같은 내용을 두 번 보여 주는 것 같아 영상은 내리고 GIF만 남겼다. 블로그를 다른 사람에게 설명할 발표 스크립트도 워드 파일로 만들었다.

## 수업내용 요약 (9부 서비스화·배포·운영 · N045~N053)

9부는 AI 기능 하나를 "남이 쓰는 서비스"로 바꾸는 과정이었다. 같은 서비스(AI 친구 에이전트 `friend-agent`)를 아홉 강의에 걸쳐 키웠고, 앞 강의가 남긴 한계를 다음 강의가 받아서 풀었다. 관통하는 한 문장은 **"성공했다는 표시와 사용자가 실제로 겪은 일은 다르다"**이다.

### N045 · AI 기능을 서비스로 설계하기

- 사용 맥락 → 처리 방식과 오류 대응 → 코드 없이 검증 → 시퀀스·아키텍처·데이터 모델 → PRD 순서로 설계한다.
- ASP에 적용해 PD 인터뷰로 "1차 사용자는 작가가 아니라 PD"임을 발견했다.
- 남은 한계: 배포·키·비용·장애는 아직 없음.

### N046 · AI 서비스 인 프로덕션

- Cloud Run 배포 한 줄 뒤에는 빌드 → 이미지 → 리비전 → 인스턴스 → URL 다섯 단계가 있다.
- 배포마다 리비전이 생기므로 롤백은 트래픽을 되돌리는 일이다. 키는 Secret Manager에 둔다.
- 키 없이 배포하자 터미널은 "포트"를 말했지만 진짜 원인은 로그의 키 누락이었다.

### N047 · Cloud Run에서 AI 서비스 운영하기

- 타임아웃·인스턴스 수·동시성·콜드 스타트·로그가 운영의 기본 손잡이다.
- 타임아웃 3초에서 답이 잘렸는데 상태 코드는 200이었다.
- 부하 테스트에서 최대 인스턴스 숫자보다 순간 스케일업 속도가 먼저 막혔다.

### N048 · GitHub Actions로 자동 배포하기

- WIF로 키 파일 없이 GitHub이 Google Cloud에 배포한다. 권한은 최소로.
- 환경변수 오류는 배포가 실패해 이전 리비전이 계속 응답했고, 시간대 오류는 배포가 성공한 채 8시 약속이 17시로 저장됐다.
- 자동 배포는 "켜지는지"만 확인한다.

### N049 · CI 테스트와 staging 환경 만들기

- CI(자동 테스트), 브랜치 보호(통과해야 머지), staging(사람이 먼저 써 봄), 배포 승인의 세 겹 게이트.
- CI는 실패를 알려 줄 뿐 막지 못한다. 막는 것은 브랜치 보호다.
- 보내기 버튼이 사라진 변경은 자동 검사를 모두 통과했고 staging을 열어 본 사람만 발견했다.

### N050 · Dockerfile로 실행 환경 정하기

- 코드가 같아도 서버에 운영체제 프로그램이 없으면 기능이 안 된다. 실행 환경도 Dockerfile로 적는다.
- 로컬에서 되던 사진 읽기(OCR)가 staging에서 500 → 설치 줄 추가 후 네 곳 모두 같은 결과.
- 같은 Dockerfile을 두 번 빌드하면 패키지는 같아도 이미지 ID가 다르다.

### N051 · 한 번 만든 이미지로 배포하기

- 이미지를 한 번만 만들고, staging에서 확인한 다이제스트를 그대로 production에 승격한다.
- 승격 뒤 두 환경의 다이제스트가 일치했고 production 배포 시간이 1분 26초 → 46초로 줄었다.

### N052 · 로드밸런서로 무중단 배포 구성하기

- 서버 두 벌(blue·green) 앞에 로드밸런서를 두고 설정만 바꿔 전환·롤백한다.
- 전환 실패 0건인데 메모리에 있던 대화는 사라졌다. 대화를 Supabase로 옮기자 유지됐다.
- 전환 성공은 곧 무중단이 아니다.

### N053 · Cloud Run으로 무중단 배포하기

- 새 버전을 0%로 올리고, 태그 URL로 스모크 테스트를 한 뒤, 통과해야 전환한다. 문제가 생기면 원클릭 롤백.
- 기본 프로브에서는 배포 성공 뒤 503 54건, `/health` 프로브로 바꾸자 0건(대신 배포 27초 → 약 84초).
- 배포 성공은 "사용자가 오류를 보지 않았다"는 증거가 아니다.

## 클로의 피드백

### 기술 질문 답변

- **좋은 점**: "늦더라도 정확한 작업이 최선"은 N053의 핵심 판단을 정확히 짚었다. 실습 숫자로 보면 확인 경로를 `/health`로 바꾸자 배포가 27초에서 약 84초로 늦어졌지만, 사용자 요청 실패는 54건에서 0건이 됐다. 느려진 1분과 사용자가 본 오류 54건을 맞바꾼 셈이다.
- **개선점**: 질문의 세 부분 가운데 "화면은 무엇이라고 했나(배포 성공)"와 "실제로는(503 54건)", "붙인 장치(`/health` 프로브, 0% 배포와 스모크 테스트)"가 답에는 빠져 있어 위 요약으로 채웠다. [책에 실을 때는 "배포 성공 메시지와 실패 54건이 같은 시각에 떠 있었다"는 장면 하나로 시작한 뒤 "늦더라도 정확하게"로 맺으면 오늘 특별편과 같은 흐름이 된다.]

### 에세이 질문 답변

- **좋은 점**: 그림(마우스)과 말 두 통로가 모두 어려웠다고 솔직하게 적었다. 전달은 아는 것과 다른 기술이라는 점을 몸으로 겪은 기록이고, 기타 에피소드의 "고민해야 하는 숙제다"와도 이어진다.
- **개선점**: 어떤 단어에서 어떻게 그렸는데 상대가 무엇으로 알아들었는지 같은 구체적인 한 장면, 그리고 28년 동안 보고·발표에서 써 온 방법과의 비교가 아직 비어 있다. [오늘 블로그 발표에서 그림 1(아홉 강의 흐름도)을 먼저 보여 준 것처럼 "그림 한 장을 먼저, 말은 그 뒤에"가 통했는지 한 줄 덧붙이면, 게임에서 느낀 숙제와 발표 경험이 한 문단으로 이어진다.]
