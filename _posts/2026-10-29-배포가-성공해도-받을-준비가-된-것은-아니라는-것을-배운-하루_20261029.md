## 오늘 배운 내용

- Cloud Run으로 무중단 배포하기(N053)를 배웠다.
- 어제 배운 무중단 배포를, 이번에는 사람이 Cloud Run에서 직접 작동시켜 보는 것이었다.

## 수업내용 요약 (N053 · Cloud Run으로 무중단 배포하기)

### 1. Cloud Run이 맡는 것과 내가 정하는 것

- Cloud Run은 로드밸런서를 운영하고, 리비전 사이의 트래픽 설정으로 요청을 옮기고, 이전 인스턴스에 종료 신호를 보낸 뒤 정리한다. 어제 Nginx 설정을 손으로 고치던 일을 Cloud Run이 맡는다.
- 새 리비전이 언제 준비됐다고 볼지는 내가 스타트업 프로브로 정한다. 기본값은 포트가 열렸는지만 보므로, 앱이 아직 준비되지 않았는데도 트래픽이 넘어갈 수 있다. 확인 경로를 `/health`로 바꾸면 이 문제를 막는다.
- 배포 성공은 Cloud Run이 정한 준비 조건을 통과했다는 뜻일 뿐이다. 사용자가 오류를 보지 않았다는 뜻은 아니다.

### 2. 대화가 남는 서비스

- staging과 production을 Supabase에 연결하고 secret key는 시크릿으로 넣어, 새 리비전이 떠도 대화가 남고 두 리비전이 같은 데이터를 보게 했다.
- 대신 두 리비전이 같은 테이블을 함께 쓰게 되므로, 코드를 되돌려도 이미 바뀐 데이터는 되돌아가지 않는다.

### 3. 블루그린, 카나리, 트래픽 고정

- 새 버전을 트래픽 0%로 올리고(`--no-traffic --tag green`) 태그 URL로 먼저 확인한 뒤 전환한다. 사용자에게 보내기 전에 새 버전을 볼 수 있다.
- 트래픽 비율을 10%, 50%, 100%로 나눠 옮기는 카나리를 해 보았다. 롤백은 이전 리비전으로 트래픽을 되돌리는 것이다.
- 트래픽을 특정 리비전에 고정해 두면 다음 배포가 만들어져도 사용자는 옛 버전을 본다. 그래서 마지막에 `--to-latest`로 고정을 풀어 둔다.

### 4. 손 작업을 워크플로로

- 손으로 하던 0% 배포, 스모크 테스트, 전환을 GitHub Actions 워크플로의 단계로 옮겼다. 스모크 테스트가 실패하면 전환하지 않고 멈춘다.
- 롤백도 버튼 하나(`workflow_dispatch`)로 실행되게 만들고, 일부러 망가뜨린 버전으로 시험했다.
- 자동화는 명령을 자동으로 치는 일이 아니라, 검증이 실패하면 다음 단계가 실행되지 않게 통제하는 일이다.

### 5. 오늘 직접 확인한 숫자 (3~7장)

- 기본 배포 요청 285건에 실패 3건. 준비가 30초 늦은 버전은 배포 명령이 37초 만에 성공으로 끝났는데 요청 295건 중 503이 54건(약 21초) 나왔다. 확인 경로를 `/health`로 바꾼 뒤에는 준비가 늦은 버전에서도 실패 0건이었다.
- 0% 배포 후 카나리 10% → 50% → 100%로 옮기는 동안 요청 503건에 실패 0건이었다.
- 롤백 직후에는 4건이 실패했다. 롤백은 준비를 확인하지 않고 곧바로 트래픽을 옮기기 때문이다. 원인은 콜드 스타트로 추정할 뿐 확인하지 못했다.
- 머지 한 번으로 돌아간 production 배포 워크플로는 전 단계 성공, 전체 2분 13초였다.

### 6. 코딩을 AI에게 맡겨도 이해해야 할 세 가지

- 준비 상태와 실행 상태는 다르다. 서버가 실행 중이어도 요청을 처리할 준비가 안 되었을 수 있다.
- 코드 롤백과 데이터 롤백은 다르다.
- 자동화와 검증은 다르다. 배포가 자동으로 끝났다는 사실만으로 무중단이 증명되지는 않는다.

## 기술 질문과 답변

**질문**: 오늘 실습에서 준비가 30초 늦은 버전을 배포하자, 배포 명령은 성공으로 끝났는데 사용자 요청은 약 21초 동안 503이었습니다. "배포 성공"과 "사용자가 오류를 안 봤다"가 왜 다른지, 그리고 스타트업 프로브를 `/health`로 바꾼 것과 0%로 올려 태그 URL로 먼저 확인한 것이 각각 이 간극을 어떻게 줄이는지 본인 말로 설명해 주세요.

**답변**: 배포를 성공하더라도 그곳이 받을 준비가 되어 있는지, 실제 요청을 처리할 수 있는 상황인지와는 다른 경우가 많다.

※ 위 답변은 앞부분(배포 성공과 사용자 경험이 다른 이유)만 다루고 두 장치에 대한 설명은 없어서, 오늘 실습 기록(제출보고서 3·4절)의 값을 아래에 덧붙인다.

- 간극이 실제로 나타난 장면: 준비가 30초 늦은 버전에서 배포 명령은 37초 만에 성공으로 끝났지만, 사용자 요청은 295건 중 54건이 503이었다(약 21초).
- 스타트업 프로브를 `/health`로 바꾼 것: "포트가 열렸는가"가 아니라 "앱이 요청을 받을 준비가 되었는가"를 기준으로 삼아, 준비가 안 된 새 리비전에는 트래픽이 가지 않게 했다. 바꾼 뒤에는 준비가 늦은 버전에서도 실패 0건이었다.
- 0%로 올려 태그 URL로 먼저 확인한 것: 사용자 트래픽을 보내기 전에 새 리비전의 `/health`와 `/version`을 직접 확인한다. 스모크 테스트가 실패하면 전환하지 않는다.
