## 수업내용 요약 (N050 · Dockerfile로 실행 환경 정하기)

### 1. 같은 코드인데 서버에서만 안 된 이유

- 오늘의 사건: 로컬에서는 되던 사진·PDF 글자 읽기(OCR)가 staging에서만 500 오류가 났다. 코드는 같았고, 서버에 `tesseract`라는 운영체제 프로그램이 없는 환경 문제였다.
- 문제를 코드·환경·배포 문제로 나눠 본다. CI 통과와 배포 성공은 "실행 환경이 맞다"는 증거가 아니다. CI는 테스트에서 확인한 조건만 보고, 테스트가 도는 GitHub 러너와 staging 이미지는 서로 다른 실행 환경이다.
- 원인은 화면에 보이는 안내 문구가 아니라 Cloud Run 로그의 ERROR 한 줄에서 찾았다.

### 2. 라이브러리와 시스템 의존성

- `pytesseract`나 `pdf2image`는 `pip`로 설치하는 파이썬 라이브러리이고, `tesseract`나 `pdftoppm`은 운영체제 프로그램이라 `pip`로는 설치되지 않는다.
- 새 기능을 붙일 때는 "파이썬 라이브러리 말고 운영체제에 설치할 프로그램이 있는가"를 먼저 묻는다.

### 3. 이미지와 컨테이너

- 이미지는 바뀌지 않는 실행 패키지이고, 컨테이너는 그것으로 만든 실행 중인 것이다. Cloud Run의 리비전은 이미지와 설정, 인스턴스는 실행 중인 컨테이너에 해당한다.
- 컨테이너를 지우고 같은 이미지로 다시 띄우면 컨테이너 메모리의 내용은 사라진다. 유지할 데이터는 외부 저장소에 둔다.
- 포트(`-p`)로 컨테이너와 바깥을 이어 요청을 보낸다.

### 4. Dockerfile과 레이어 캐시

- 베이스 이미지, 시스템 패키지, 라이브러리, 코드, 실행 사용자, 시작 명령을 한 파일에 적어 저장소에 넣으면 어디서 빌드해도 같은 실행 환경을 만든다.
- 줄 하나가 레이어 하나다. 바뀌지 않은 줄은 이전 레이어를 다시 쓰므로 오래 걸리는 설치는 위에, 자주 바뀌는 코드 복사는 아래에 둔다.
- 검토 5기준은 베이스 이미지 버전 고정, 필요한 시스템 패키지, `.dockerignore`에 `.env`, `PORT` 환경변수, non-root 사용자다. API 키는 이미지에 넣지 않고 실행할 때 건넨다.

### 5. 기존 자동 배포에 얹기

- 소스 배포는 Dockerfile이 있으면 buildpacks 대신 그것으로 빌드한다. 자동 베이스 이미지 업데이트와 충돌하므로 `--clear-base-image` 한 단어만 추가했다.
- Cloud Build 기록에서 `Dockerfile`과 설치 단계가 실제로 돌았는지 확인한다.
- 올라가는 파일은 `.dockerignore`, `.gcloudignore`, Git 커밋 대상으로 세 번 확인한다.

### 6. 오늘 직접 해본 것

- 로컬 OCR 성공, staging 500 재현, Dockerfile 작성, 로컬 컨테이너 확인을 거쳐 PR #20~#23으로 staging과 production까지 배포했다. production은 직접 승인했다.
- 같은 사진을 로컬, 로컬 컨테이너, staging, production 네 곳에 보내 모두 200 · 153글자 · 같은 결과 해시를 확인했다.
- `.dockerignore`가 하위 폴더의 `__pycache__`를 놓쳐 이미지에 .pyc 17개가 들어간 것을 이미지 안을 열어 보고 발견해 고쳤다.
- 과제 3으로 PDF 읽기(poppler)를 붙였다. poppler 줄이 없던 로컬 컨테이너에서만 PDF가 500이었고, Dockerfile에 `poppler-utils` 한 줄을 더해 해결했다.
- 같은 Dockerfile로 두 번 빌드해도 패키지 목록은 같고 이미지 ID는 달랐다.
