## 오늘 배운 내용
N034 폴더에서 카드뉴스를 만드는 법을 배웠다. 결국은 AI와 사람이 할 일을 명확히 구분하는 것에서 시작한다는 것, 즉 Human-in-the-Loop라는 개념이 오늘 실습의 핵심이었다.

## 수업내용 요약 (N034 · 카드뉴스 에이전트)

### 챕터 1 · 사용자와 함께 완성하는 제작 흐름
- 목표는 "AI가 카드뉴스를 다 만들어주는 앱"이 아니라, AI가 조사·기획·제작하고 중요한 순간마다 사람이 선택·검토·승인하는 "에이전틱 워크플로(Agentic Workflow)"를 만드는 것.
- 전체 흐름은 7단계: 주제 입력 → 정보 선택 → 심층 조사·편집 판단 → 스토리보드 승인 → 이미지·글자 제작 → 검수·부분 수정 → 승인·다운로드.
- 핵심 개념은 "사용자의 선택 자체가 워크플로의 상태(state)"라는 것. 화면이 후보 선택 앞에서 멈춰 있는 건 고장이 아니라 사용자의 결정을 기다리는 정상 상태.

### 챕터 2 · 카드뉴스 형식과 독자 선택
- 디자인보다 먼저 "독자·핵심 메시지·행동"을 정해야 형식과 문구가 자연스럽게 따라온다.
- 캐러셀(여러 장 넘겨보는 형식)에서 첫 장의 시선을 붙잡는 문구가 "후킹(Hooking)". 독자가 얻을 변화를 직접 보여주는 문구일수록 후킹이 강함.
- 5가지 참고 형식(단계 안내형·체크리스트형·사진 중심 연속형·이야기형·목록·비교형)을 독자가 그 카드뉴스를 보는 목적에 맞춰 고른다.
- 이미지 저작권은 CC0(퍼블릭 도메인)·라이선스 스톡·AI 생성·저작권 불분명(사용 금지) 4가지로 구분.

### 챕터 3 · PRD로 시작하는 바이브코딩
- 완성된 코드를 따라 치지 않고, PRD(제품 요구사항 문서) 한 장을 개발 도우미에게 전달해 대화로 앱을 완성해가는 방식이 "바이브코딩(Vibe Coding)".
- 처음부터 "전체를 완성해 달라"고 요청하지 않고, 아직 정하지 않은 것을 개발 도우미가 먼저 찾아내게 하고 결정은 DECISIONS.md에 기록.
- 구현 언어와 실행 엔진(Claude Agent SDK / Claude CLI / OpenCode CLI) 중 하나만 선택.
- "개발 단계의 질문"(개발 도우미 → 개발자)과 "실제 사용 단계의 질문"(완성된 제작 에이전트 → 사용자)을 헷갈리지 않아야 함.
- 모의 데이터 → 실제 AI 조사 연결 → 이미지 한 장 → 후킹 별도 설계 → 부분 수정 순으로 단계적으로 연결. 참고 구현에는 알려진 한계가 있어 그대로 믿으면 안 됨.

### 챕터 4 · 실행 엔진과 웹 질문 연결
- 핵심은 "AI를 웹앱에 붙이는 것"이 아니라 "AI의 중단과 재개를 웹앱의 상태로 관리하는 것".
- 세션(Session)은 AI와의 이전 대화·작업 맥락을 이어가는 단위. running ↔ waiting_for_user ↔ completed/failed 상태 전이로 관리하며, waiting_for_user는 오류가 아니라 정상 상태.
- SDK는 canUseTool/can_use_tool 콜백으로, CLI는 앱이 정한 need_input 규약(question_id·version 포함)으로 질문을 처리.
- 새로고침(서버는 살아있음)과 서버 재시작(메모리 상태 소실)은 서로 다르게 대응해야 함 — "세션 ID 저장 ≠ 작업 상태 자동 복구".

### 챕터 5 · AI 최신소식으로 제작과 검수
- 최근 7일 소식을 조사(부족하면 30일로 확대할지 질문), 7~12개 후보 제시 → 1~3개 선택 → 심층 검증(확인한 사실·발표 주체 주장·미확인 내용을 구분하고 근거 링크 부착).
- 독자·후킹이 정해지면 5~8장 스토리보드(한 장에 메시지 하나만), 표지 후킹이 원문보다 과장되지 않게 주의.
- Antigravity(agy) CLI로 이미지 생성(1024×1024 PNG, 글자 없음) → 최종 카드는 1080×1350으로 렌더링, 제목·본문은 별도 텍스트 레이어로 배치.
- 검수는 화면의 초안이 아니라 "내보낸 파일" 기준(최신성과 사실·독자와 흐름·생성 결과·편집과 가독성·실패와 재시도·내보내기, 6개 기준).

### 챕터 6 · 나만의 워크플로로 확장하기
- "조사 → 후보 비교 → 사람 선택 → 생성 → 검수 → 저장" 구조는 카드뉴스에 국한되지 않고 회의록 정리, 복습 문제 생성 같은 다른 반복 업무에도 그대로 이식 가능.
- 새 워크플로를 설계할 때는 입력 / AI 판단 / 사람 결정 / 도구 행동 / 검수 산출물, 5가지를 각각 정의.
- 제출물 구성: README.md, PRD.md, DECISIONS.md, API_SPEC.md, ACCEPTANCE.md, VALIDATION.md.

## 클로의 피드백
**좋은 점**
- 기술 답변에서 "개발 방법을 정할 때 클로가 적절한 순간에 물어봐줬고, 결과도 눈으로 직접 확인했다"는 대응은, 오늘 자료의 "waiting_for_user는 정상 상태"와 "검수는 화면 초안이 아니라 내보낸 파일 기준"이라는 두 개념을 실제로 몸으로 체험한 것과 정확히 겹친다. "내 제안으로 프로젝트에 카드뉴스 생성을 확장했다"는 부분도 챕터 6의 "구조는 재사용된다"를 스스로 실천한 사례다.
- 에세이 답변의 "칼럼을 간추려 핵심부터 전달하고, 전체를 읽으려면 다시 칼럼으로 돌아오게 만든다"는 아이디어는, 오늘 배운 "독자가 카드뉴스를 보는 목적에 따라 형식을 고른다"는 개념과 "카드뉴스 → 원문"으로 이어지는 CTA 구조를 브런치 연재에 그대로 접목한, 매우 구체적인 설계다.

**개선점**
- `[책에 실을 때 보완하면 좋을 부분]` 기술 답변에 "구체적으로 어떤 순간에 멈춰서 확인했는지"(예: 엔진 선택 시점인지, 이미지 생성 결과 확인 시점인지) 한 문장만 더 붙이면 오늘 배운 waiting_for_user 개념과 더 정확히 맞아떨어질 것 같다.
- `[에세이 보강 여지]` "칼럼 요약 → 다시 칼럼으로 돌아오는 방법"이 오늘 배운 5가지 참고 형식(단계 안내형·체크리스트형·사진 중심형·이야기형·목록·비교형) 중 어느 쪽에 가까운지 한 번 연결해보면, 브런치용 카드뉴스 설계가 한 단계 더 구체화될 것 같다.
