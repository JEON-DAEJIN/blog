## 오늘 배운 내용

오늘은 "도구 설계 — 에이전트에게 무엇을 줄 것인가?"를 배웠다. QuestB를 수행하는 동시에, 직접 챗봇을 설계하는 과제도 제출했다.

## 수업내용 요약

**N026 · 도구 설계(Tool Design) — LLM 에이전트가 도구를 안전하게 쓰게 만드는 법**

- **도구 호출의 세 가지 실패와 하네스**: 도구를 쥐여준 에이전트가 겪는 실패는 ① 잘못 고름(도구 선택 실패) ② 잘못 읽음(결과 해석 실패) ③ 같은 실수 반복(학습 없는 순환)의 세 순간으로 나뉜다. 이를 이해하려면 모델(다음 텍스트를 고르는 엔진)·에이전트(과업 판단·행동 결정)·하네스(허용목록 확인·인자 검사·실행·결과 재입력을 담당하는 집행 장치)·루프(호출-실행-판단의 순환)를 구분해야 한다.
- **도구 설명은 모델이 읽는 프롬프트다**: 도구는 함수가 아니라 이름·설명·인자 스키마·반환 형식·실패 뒤 행동을 묶은 "계약"이며, 이 계약 전체가 시스템 프롬프트에 그대로 주입된다. 도구 전달 방식은 텍스트 규약(ReAct) → 네이티브 함수 호출 API(OpenAI 2023, Anthropic tool_use) → MCP(Anthropic, 2024-11-25 공개 표준) 순으로 발전해왔다.
- **도구 정의서 6항목과 minimal vs contextual 실습**: 이름 / 하는 일 한 문장 / 언제 쓰고 안 쓰는지 / 인자 스키마 / 반환 형식 / 실패 정의와 뒤 행동, 이 6항목으로 도구를 "계약"으로 만든다. 같은 도구를 설명만 다르게(minimal vs contextual) 등록해 실행하면, 언제·실패 시 행동이 비어 있는 minimal 쪽에서 실패가 재현된다. 한 번에 한 곳만 고쳐 전후를 비교하는 것이 원칙.
- **하네스의 6개 설계 지점**: ① 시스템 지시 → ② 도구(계약) → ③ 권한 → ④ 실행 환경 → ⑤ 관찰 → ⑥ 중단. "같은 모델, 다른 하네스는 다른 에이전트"라는 원칙이 SWE-agent, mini-swe-agent, Aider 세 사례로 뒷받침된다. 관찰(⑤)은 잘못 읽은 순간을 찾아 다음 설계를 고칠 수 있게 해주는 "계기판" 역할.
- **실습: 도구 직접 만들기 + RAG를 MCP로 붙이기**: LangChain `@tool`로 `get_inventory`를 구현해 [모델 요청]→[하네스 실행]→[최종 답] 3단계를 트레이스로 확인. Qdrant를 `mcp-server-qdrant`로 감싸 Claude Code와 opencode 등 서로 다른 에이전트에 각자의 설정 문법으로 등록해도 결국 같은 서버 실행 지점으로 모인다는 것을 확인.
- **권한과 신뢰 경계 — 4층 방어**: 도구 설명·스키마는 안내일 뿐 실제 제한이 아니다. 입력층(구분자·격리) / 모델층(비신뢰 입력 학습) / 하네스층(최소 권한·승인, 가장 두꺼운 실행 경계) / 운영층(평가·감시), 이 4개 층이 함께 있어야 프롬프트 인젝션 같은 공격에 대응할 수 있다.
- **과제 — 서비스 가이드 챗봇 설계**: 서비스 하나를 골라 design-packet.md(시스템 지시 초안 / 도구 계약 3~4개 / 권한과 승인 / 오류·보류·이관 규칙 / 반환 형식 규약 / 테스트 문항 6~8개 / 트레이스 양식)를 작성하는 과제. 테스트 문항에는 "공격 사례"(예: 승인 절차 무시 요청)도 포함해, 도구를 실행하지 않고 절차를 안내하는 것이 기대 응답임을 확인한다.
- **도구 사용 평가와 회귀 확인**: 최종 답의 자연스러움이 아니라 도구 선택 / 스키마 준수 / 반환 근거 / 실패 처리 4항목을 각각 이진(pass/fail)으로 판정한다. 수정 후에는 새로 실패한 문항만이 아니라 수정 전 테스트 세트 전체를 재실행해 회귀 여부를 확인해야 한다.
- **4대 안티패턴**: 도구 남발(잘못 고름) / 데이터 덤프(잘못 읽음) / 권한 방치(세 순간 전반) / 중단 없는 순환(같은 실수 반복). 도구가 많다고 능력이 커지는 게 아니라, 필요한 순간에 올바른 도구를 찾을 수 있어야 한다.

## 인상적인 장면

오늘은 모두 차분한 분위기에서 수업이 진행됐다. 다만 점점 힘들어하는 모습들이 눈에 보였다.

## 어려웠던 점과 극복 과정

챗봇 프로젝트를 적용해볼 나만의 아이템을 찾느라 고생했다. 나중에 실제로 붙여서 쓸 것이라 생각해서, 결국 메인도메인과 연계할 수 있는 storytowebtoon 프로젝트와 엮는 쪽으로 정리했다.

## 새롭게 알게 된 점 — 커리어와의 접점

챗봇을 여러 곳에서 서비스로 받아보기도 하고 직접 만들어보기도 했지만, 생각만큼 어렵지 않게 구현할 수 있다는 점에서 놀랐다. 하지만 바이브코딩을 직접 해보면서, 생각보다 훨씬 더 정교하게 설계해야 한다는 점에서 다시 한번 놀랐다.

오늘 배운 "도구 계약"과 "권한·승인 경계"는 신규사업 기획이나 조직 경영에서 다루던 것과 본질이 같다. 담당자(도구)에게 "언제 이 일을 처리하고 언제 상급자에게 이관하는지", "실패했을 때 어떤 절차를 밟는지"를 명문화하지 않으면 조직이 같은 실수를 반복하는 것처럼, 에이전트도 도구 정의서에 그 경계가 없으면 같은 실패를 반복한다. "같은 모델, 다른 하네스는 다른 에이전트"라는 원칙도, 같은 인력이라도 조직 설계(권한 위임 구조, 보고 체계)에 따라 완전히 다른 성과를 내는 경영 경험과 정확히 겹쳐 보였다.

## 기술 질문과 답변

**Q.** 오늘 자료의 핵심은 "도구 정의서 6항목"(이름/하는 일/언제 쓰고 안 쓰는지/인자 스키마/반환 형식/실패 정의)과 "하네스 6개 설계 지점"(시스템 지시→도구→권한→실행 환경→관찰→중단)을 분리해서 설계해야 한다는 것이었습니다. 오늘 QuestB 실습이나 직접 설계한 서비스 가이드 챗봇 과제에서, 이 둘 중 어느 항목을 채우기가 가장 까다로웠나요? 구체적으로 어떤 도구/기능을 놓고 어떤 항목(예: "언제 쓰고 안 쓰는지" 또는 "실패 뒤 행동")이 비어 있었는지, 그리고 어떻게 채웠는지 말씀해주세요.

**A.** 결국 모든 에러를 다 가정할 수 없으니, 반환과 실패를 정의하고 그에 맞는 프롬프트를 정의할 수 있어야 한다고 봐.

## 에세이 질문과 답변

**Q.** 메모에서 "챗봇 프로젝트를 적용해볼 나만의 아이템을 찾느라 고생했고, 결국 storytowebtoon 프로젝트와 연계시켰다"고 하셨는데요. 다른 후보들도 고민하셨을 텐데, 왜 결국 storytowebtoon과 엮기로 결정하셨나요? 그리고 "바이브코딩을 해보면서 생각보다 더 정교하게 설계해야 한다는 걸 다시 한번 놀랐다"고 하신 순간 — 오늘 어떤 구체적인 장면에서 그걸 느끼셨나요?

**A.** 내가 이 과정을 통해 진행해보고 싶었던 메인도메인인데다가 어느 정도 실물 폼도 완성한 상태라, 여기에 적용하는 게 맞다고 봤음.

## 클로의 피드백

- **좋은 점**: 기술 질문 답변이 "완벽한 실패 목록을 만들 수는 없다"는 전제를 정확히 짚었다. 오늘 자료의 부록 B(트러블슈팅)와 8장(회귀 확인)이 강조하는 것도 결국 같은 원칙 — 실패를 미리 다 막으려 하지 말고, 반환·실패 정의와 그에 맞는 프롬프트(모델의 뒤 행동)를 설계해두라는 것이다. 에세이 답변도 "메인도메인 + 이미 실물 폼이 있는 프로젝트"라는 두 가지 기준을 명확히 제시해, 왜 storytowebtoon을 골랐는지 논리가 분명하다.
- **개선점**: `[책에 실을 때 보완하면 좋을 부분]` 기술 질문에 "구체적으로 어떤 도구/기능을 놓고 어떤 항목이 비어 있었는지"를 물었는데, 답변은 일반 원칙 수준에 머물렀다. 실제 design-packet.md에서 어떤 도구 계약 문장을 고쳤는지 한 문장만 더 붙이면, 오늘의 실습이 훨씬 또렷하게 기록에 남을 것이다.
