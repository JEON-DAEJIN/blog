## 오늘 배운 내용

- 한 번 만든 이미지로 배포하기(N051)를 배웠다.

## 수업내용 요약 (N051 · 한 번 만든 이미지로 배포하기)

### 1. 자동 배포 다음에 오는 세 질문

- production에서 문제가 났을 때 답해야 하는 세 가지가 있다. 지금 도는 코드가 어느 커밋인가(추적성), 정상이던 버전으로 되돌릴 수 있는가(복구성), staging에서 확인한 이미지와 같은가(동일성)이다.
- 소스로 배포하던 기존 구조에서는 이미지에 커밋이 적혀 있지 않았고, 환경마다 이미지를 따로 빌드해서 세 질문 모두 답하기 어려웠다.

### 2. 이미지 이름, 태그, 다이제스트

- 이미지 이름은 리전 주소 / 프로젝트 / 저장소 / 이미지 이름 : 태그로 이루어진다.
- 태그는 다른 이미지로 옮겨 붙을 수 있는 이름표이고(`latest`의 문제), 다이제스트(`sha256:…`)는 이미지 내용으로 정해지는 지문이다.
- Cloud Run 리비전은 태그로 배포해도 그 순간의 다이제스트로 고정해 기록한다.

### 3. Actions에서 이미지를 한 번만 만들기

- 이미지 빌드 주체를 Cloud Build에서 GitHub Actions로 바꾸고, 커밋 SHA를 태그로 붙여 `friend-agent` 저장소에 올린다.
- 권한은 프로젝트 전체가 아니라 저장소 하나에 `artifactregistry.writer`만 준다(최소 권한). API 키는 빌드 인자로 넘기지 않고 실행할 때 Secret Manager에서 읽는다.

### 4. 연결표와 이미지 승격 (build once, deploy many)

- 커밋 SHA → 이미지 태그 → 다이제스트 → 리비전 → `/version` 다섯 칸을 잇는 연결표로 지금 도는 코드를 추적한다.
- 승격은 staging에서 확인한 이미지를 다시 빌드하지 않고 다이제스트 그대로 production에 보내는 것이다. 먼저 명령 한 줄로 해 본 뒤 배포 워크플로의 세 군데를 고쳐 자동화한다. 승격할 때 `COMMIT_SHA`도 함께 바꾸고 `--update-env-vars`만 쓴다.
- 승격 후 production 승인의 뜻이 "새로 만든 이미지"에서 "staging에서 확인한 그 이미지"로 바뀐다.

### 5. 로컬에서 만든 이미지를 올리지 않는 이유

- CPU 아키텍처 불일치(Apple Silicon의 arm64와 Cloud Run의 amd64)와, 어떤 커밋으로 만들었는지 기록이 끊기는 문제가 있다.
- 그래서 배포용 이미지는 Actions에서만 만든다는 규칙을 `AGENTS.md`에 적는다.

### 6. 정리 정책과 고장 난 Dockerfile

- 정리 정책은 삭제 정책과 유지 정책을 함께 걸고, 드라이런으로 먼저 확인한다. 롤백에 필요한 이미지는 남긴다.
- 고장 난 Dockerfile 네 가지(시스템 패키지 누락, `.dockerignore`의 `.env`, 실행 사용자, 고정 포트)를 증상만 보고 원인을 찾는다.
- 장애 대응 훈련을 처음과 마지막에 두 번 해서 걸린 시간을 비교한다.

## 기술 질문과 답변

**질문**: staging과 production에서 도는 이미지가 "같다"고 말하려면 무엇을 비교해야 하는지, 그 비교에 커밋 SHA 태그가 아니라 다이제스트를 쓰는 이유는 무엇인지 본인 말로 설명해 주세요. 오늘 직접 확인한 값이나 화면이 있다면 함께 적어 주세요.

**답변**: staging과 production의 이미지가 같은지 확인하려면 각 Cloud Run 리비전 상세에 표시된 이미지 다이제스트를 비교해야 한다. 커밋 SHA 태그는 이동할 수 있는 이름이지만, 다이제스트는 이미지 내용을 식별하기 때문이다.

오늘은 staging에서 검증한 이미지를 다이제스트 주소 그대로 production에 승격하는 구조를 학습했다. 실제 확인 결과는 두 환경의 리비전 상세에 표시된 다이제스트가 동일한지 비교해 기록한다.

- staging 다이제스트: [실제 확인한 값]
- production 다이제스트: [실제 확인한 값]
- 비교 결과: [동일 / 다름]

※ 위 세 줄은 답변에 빈칸으로 남아 있어, 오늘 실습 기록(제출보고서 4·8절)의 값을 아래에 덧붙인다.

- staging 다이제스트: `sha256:d339e5d333ec…` (리비전 `friend-agent-staging-00010-zx9`)
- production 다이제스트: `sha256:d339e5d333ec…` (리비전 `friend-agent-00023-8ht`)
- 비교 결과: 승격 직후에는 동일했고 `/version`의 commit도 둘 다 `8243335`였다. 그 뒤 PR #28이 staging에만 머지되어 지금 staging은 `c87c9b5279f8`(`1010a7d`)로 앞서 있다.
