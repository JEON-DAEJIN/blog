## 오늘 배운 내용

- Cloud Run에서 이미 배포한 AI 서비스를 운영하는 법(N047)을 배웠다.
- 어제 만든 friend-agent 서비스를 조원과 서로 바꿔 실제로 써보는 실습을 진행했다.

## 수업내용 요약 (N047 · Cloud Run에서 AI서비스 운영하기)

### 1. 공개한 뒤에는 질문이 바뀐다

- 서비스가 올라간 뒤에는 질문이 "올라갔나?"에서 "계속 잘 도나?"로 바뀐다.
- AI 서비스는 답이 느리고, 요청마다 LLM 제공사에 비용이 들며, 처리 시간이 들쭉날쭉해서 같은 Cloud Run 위에서도 요청 타임아웃·인스턴스 수·사용 한도를 AI 서비스에 맞게 따로 정해야 한다.
- 공개 주소를 단체 대화방에 올렸을 때 생길 수 있는 세 가지 문제: A) 답이 길어져 타임아웃 초과, B) 주소가 퍼져 요청 급증·비용 증가, C) 새 버전 배포 후 캐릭터·대화 소실.

### 2. 시작 상태 맞추기

- 읽기 전용 명령 세 개로 프로젝트·리전, 서비스 URL, 시크릿 존재 여부를 확인한다(시크릿 값은 출력하지 않는다).
- 에이전트에게 맡길 때도 "확인만 하고 아무것도 만들거나 바꾸지 마"라고 범위를 못 박는다.

### 3. 스트리밍과 요청 타임아웃

- 스트리밍은 피자를 한 조각씩 내놓는 것 — 답을 조금씩 전달해 사용자가 첫 글자를 일찍 보게 한다.
- 답을 보낸 뒤에도 같은 요청 안에서 "기억 정리"를 마저 하기 때문에, 타임아웃이 짧으면 두 군데서 끊길 수 있다.
- 끊긴 결과가 정상처럼 보이는 게 더 큰 문제다 — 날씨 문장이 중간에 끊기면 맑은 날로 읽히고, 기억 정리가 끊기면 답은 멀쩡한데 저장이 안 된다.
- 값은 측정으로 정한다 — P50(절반이 이 시간 이하)과 P99(99%가 이 시간 이하)를 함께 보고, 측정한 요청 전체 시간보다 넉넉하게 타임아웃을 잡는다. 늘린다고 LLM이 빨라지진 않는다.

### 4. 인스턴스 수 제한과 사라지는 데이터

- 최소 인스턴스 0은 유휴 비용 절감 대신 콜드 스타트를 받아들이는 선택이고, 최대 인스턴스는 몰릴 때 켜지는 수의 상한이다.
- 캐릭터·대화가 사라진 진짜 이유 — 템플릿이 데이터를 인스턴스 메모리에 저장해서, 새 리비전 배포나 인스턴스 교체, 요청이 없어 0개로 줄어드는 순간 메모리도 함께 사라진다.
- 인스턴스 수와 데이터 저장 위치는 별개 문제다. 남겨야 하는 데이터는 컨테이너 밖 데이터베이스에 둔다.

### 5. 최대 인스턴스로 막지 못하는 비용

- 최대 인스턴스 2 × 동시성 80 = 동시 160건, 답변 8초면 시간당 7만 2천 건 처리 가능 — 최대 인스턴스는 동시 처리 규모만 제한할 뿐 누적 호출 총량은 못 막는다.
- 총액을 막는 것은 LLM 제공사의 월 사용 한도이고, 예산 알림은 메일만 보낼 뿐 지출을 멈추지 않는다.
- 메시지 하나에 LLM을 세 번(도구 선택 → 답변 생성 → 기억 정리) 호출해서, 실제 비용 대부분은 Cloud Run이 아니라 LLM API 쪽에서 나온다.
- BYOK(사용자가 자기 키를 넣는 구조)는 비용·한도를 사용자에게 넘기는 대신 키 보안·안내 책임이 새로 생긴다.

### 6. 로그의 세 종류와 근거로 진단하기

- 요청 로그(접수 기록)·컨테이너 로그(진료 기록)·시스템 로그(시설 기록)를 구분해서 읽는다.
- "AI가 느려요, 고쳐주세요" 대신 "몇 시~몇 시 사이 5초 넘은 요청의 로그를 보고 근거를 먼저 보여줘, 아직 고치지 마"라고 요청해야 에이전트가 짐작으로 고치지 않는다.
- 일부러 환경변수를 잘못된 값으로 바꿔 배포를 실패시켜 보고, 로그 타임라인으로 원인을 재구성하는 연습을 한다.

### 7. 서로 써 보기와 추가 과제

- 서비스 URL은 식당 주소, 키는 내 결제 수단이다 — 주소를 알면 누구나 방문하고 비용은 운영자가 부담한다.
- 최대 인스턴스와 동시성을 건물에 비유하면: 최대 인스턴스는 건물 개수, 동시성은 건물 하나가 동시에 처리하는 요청 수다.
- 추가 과제 4종: 롤백 / 부하 테스트로 동시성·최대 인스턴스 확인 / 내 앱 배포 / BYOK 구조로 바꾸기.

### 8. 오늘 배운 것 — 걱정을 설정으로 나누기

- 처음 가졌던 걱정(비용·지연·데이터)을 각각 "오늘 설정이 막아주는 것"과 "아직 못 막는 것"으로 나눠 정리한다.
- 설정 하나가 모든 문제를 해결해주지 않는다는 게 오늘의 핵심 결론이다.

## 인상적인 장면

- 어제 만들어 놓은 서비스를 디벨롭해서 다시 응용하는 실습이라, 생각보다는 어렵지 않았다.

## 어려웠던 점과 극복 과정

- 어제 따라가지 못했던 부분을 집에서 예습하고 왔더니 오늘은 좀 더 수월했다.

## 새롭게 알게 된 점 — 커리어와의 접점

- 언제나 다른 사람에게 리뷰 받는 것은 어려운 일이다.
- 아무리 조그만 것이라도 배울 것이 있다.
- 그래서 나는 조금씩 성장한다.

## 기술 질문과 답변

**질문**: 오늘 부하 테스트에서 설정 B(동시성 1·최대 인스턴스 20)와 설정 C(동시성 1·최대 인스턴스 3)가 거의 똑같은 결과(15개 성공·35개 실패)가 나왔습니다. 최대 인스턴스 숫자와 실제 처리 능력 사이에 어떤 관계가 있었길래 이런 결과가 나온 걸까요? 오늘 로그에서 직접 확인한 근거를 들어 설명해주세요.

**답변**: 우리 설정의 문제라기보다는 구글 정책상 인스턴스 숫자가 작아 처리할 수 없는 물량이 당도하면 그냥 페일 처리를 내 버리는 것 같다.

## 에세이 질문과 답변

**질문**: 메모에 "다른 사람에게 리뷰 받는 건 언제나 어려운 일"이라고, 또 "아무리 조그만 것이라도 배울 게 있다"고 적어주셨어요. 오늘 조원의 routine-coach를 직접 써보면서 "아, 이건 배울 점이다"라고 느낀 구체적인 장면이 있었나요? 그리고 그 장면이 28년 경력에서 다른 사람에게 리뷰받기 어려웠던 어떤 기억과 맞닿아 있는지 이야기해주세요.

**답변**: 루틴 관리하기, 중복 아이템 구매 방지 등과 같이 생활에 꼭 필요한 아이디어를 자신의 고민을 바탕으로 구축했다는 게 놀라웠고, 다른 한 분의 프로젝트는 실제 합창단에서 활용할 프로젝트를 실제로 돌아가는 수준만큼 완벽하게 만들었다. 같은 시간을 들여 수업을 들었는데 겨우 수업을 따라가는 내 수준과 동떨어져서 부러웠다.

## 오늘의 성장도

★★★★☆ 4/5

어제보다는 짧은 시간 안에 프로젝트를 마무리하고, 다른 동료들의 프로젝트까지 리뷰할 수 있었다.

## 한 줄 소감 / 내일의 각오

동료들의 프로젝트를 보며 느끼는 게 많다. 더 노력해야겠다.

## 기타 에피소드

조원들에게 friend-agent 주소를 공유해 사용후기를 받기 시작했다. 받은 피드백 세 가지(성격 설정 불일치, 약속 임의 생성, 존댓말 미반영) 중 두 가지는 오늘 직접 겪은 문제와 정확히 겹쳤다. 조원의 routine-coach(습관 추적 앱)에 직접 접속해 체크리스트대로 리뷰도 썼다. 오늘 내용을 요약한 58초짜리 모션 영상도 만들어 Notion에 올릴 준비를 해 두었다.

## 클로의 피드백

### 기술 질문 답변

- **좋은 점**: 정확한 핵심 판단이다. "우리 설정의 문제가 아니라 플랫폼(구글) 정책의 한계"라는 지적은 오늘 로그에서 직접 확인한 `no available instance`(지연 0초) 증거와 정확히 일치한다. "설정을 더 잘 조정하면 해결된다"는 흔한 오해에서 벗어나, 플랫폼 자체의 스케일업 속도 한계를 정확히 짚었다.
- **개선점**: 답변에 실제 로그 문구(`no available instance`, 지연 0초)와 B·C 설정이 똑같이 15성공·35실패였다는 구체적 숫자를 함께 적으면 책에 실을 때 근거가 훨씬 또렷해진다.

### 에세이 질문 답변

- **좋은 점**: 부러움이라는 감정을 숨기지 않고 구체적인 장면(루틴 관리·중복 구매 방지 아이디어, 합창단 프로젝트의 완성도)으로 적었다. 추상적인 "열심히 하겠다"가 아니라 실제로 본 것에서 출발한 성찰이다.
- **개선점**: 질문의 둘째 절반 — 다른 사람에게 리뷰받기 어려웠던 28년 경력의 구체적 기억과의 연결이 아직 비어 있다. [예를 들어 스토리위즈 시절 "이거 뜨겠습니까" 질문을 받던 순간처럼, 평가받는 입장이었던 장면 하나를 다음에 보태면 좋다.]
