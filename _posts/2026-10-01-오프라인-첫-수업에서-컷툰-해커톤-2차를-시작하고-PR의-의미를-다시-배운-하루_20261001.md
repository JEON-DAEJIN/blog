## 오늘 배운 내용

해커톤을 이어 나갔다. 기업 연계 프로젝트인 컷툰(Cuttoon) 코파일럿 만들기의 2차 작업을 시작한 날이다. 오늘은 오프라인으로 만난 첫 수업이기도 했다.

## 수업내용 요약

별도 수업자료 없이 해커톤 작업을 한 날이라, 이번 세션의 메이킹로그를 바탕으로 한 일을 정리한다.

### 1. 한 달 만에 팀 저장소로 돌아오기

- 최신 코드를 받아(pull) 내 브랜치에 합치자, main에 있던 ".env 추적 제거" 커밋 때문에 내 컴퓨터의 `.env` 파일이 지워졌다. 직전 기록에서 복구했다.
- 새로 교체한 API 키를 비용이 들지 않는 조회로 검증했다. OpenAI는 정상, Supabase는 주소를 찾지 못했는데 원인은 키가 아니라 무료 프로젝트의 일시 정지였다. 복구 후 모두 정상.
- 2차 규칙을 읽었다: 4인 체제(나는 화면 전체 담당), 모든 PR은 머지 전 QA 확인, "아직 정해지지 않은 항목은 확정 전에 구현하지 않는다".

### 2. 코드 작업 ① — 진행률 표시와 유실 방지 (PR #177, main에 머지)

- 나머지 3컷을 만드는 함수가 3컷을 다 만든 뒤에야 결과를 돌려줘서, 화면이 진행 상황을 몰랐다. 컷 하나가 끝날 때마다 알려 주게 바꾸고 "1/3 → 2/3 → 3/3"을 보여 준다.
- 도중에 실패하면 이미 돈을 내고 만든 컷까지 버려지던 문제를 고쳤다. 만든 컷은 바로 저장하고, "이어서 만들기"로 다음 컷부터 재개한다.
- 실제 이미지 생성은 유료라, 서버 응답을 가짜로 바꾼 시험으로 확인했다(재개 시 서버 호출 2회만).

### 3. 코드 작업 ② — 소재 "알아서 해줘" (PR #191, 리뷰 대기)

- 정해지지 않은 부분은 코드 대신 질문 4개로 먼저 올렸고, 캡틴(chictimin)이 11분 만에 결정했다.
- 후보는 내 의견(1개)과 달리 3개로 결정됐다. "소재 선택은 품질 비교가 아니라 방향 선택"이라는 근거였다.
- 서버가 없어서 약속된 응답 모양 그대로 mock으로 먼저 만들었고, QA가 실제 서버로 통과시킨 뒤 mock을 지우고 실서버 호출로 전환했다.

### 4. 리뷰와 팀 결정

- 동료 PR 4건에 리뷰를 남겼다. 그중 #186은 이미 올라와 있던 서버 PR과 대조해 요청·응답 약속이 어긋난 곳 4군데를 찾았고, 통합 PR #198에서 모두 반영된 것을 코드로 확인한 뒤 승인했다.
- 이미지 비용 문제(#190)에는 화면 담당으로서 의견을 냈다("저가 설정 먼저, 안 되면 하이브리드"). 팀이 그대로 채택했다.

## 인상적인 장면

오늘은 오프라인 첫 수업이었다. 그런데 모두가 자주 만난 사람처럼 익숙했다. 온라인 교육에 충실하게 참여한 덕분이다.

## 어려웠던 점과 극복 과정

내가 맡은 범위가 넓어졌다. 다행히 옆에서 시민님과 정목님이 가르쳐 줬다.

평소 활용하지 않던 opencode를 다시 써 보고, open design이라는 것을 연결해 보려 했는데 잘 되지 않았다. 이건 아직 못 풀었다. 집에서 시간이 될 때 클로드 코드와 하나하나 다시 사용해 봐야겠다.

## 새롭게 알게 된 점 — 커리어와의 접점

역시 오프라인의 힘이 강하다. 온라인에서 보던 사람들을 오프라인에서 보니 더 친근하게 느껴졌다. 앞으로 어려운 상황이 여럿 생길 수 있겠지만, 함께 잘 이겨 나갈 수 있을 거라 생각한다.

## 기술 질문과 답변

**질문:** 이번 작업에서 커밋, 푸시, PR, 머지를 모두 거쳤습니다. 이 팀은 "main에 직접 올리지 않고 반드시 PR을 거친다"는 규칙을 두고 있는데, 이 규칙이 없었다면 이번에 어떤 일이 생겼을까요? PR #186에서 찾은 약속 불일치 4곳이나, PR #177의 QA 요청처럼 직접 겪은 장면 하나를 예로 들어 설명해 주세요.

**답변:** 캡틴이 나서서 이를 정리하고 승인해 주지 않으면, 뒤늦게 온 것이 앞의 것을 덮어써서 성능 개선이 이뤄지지 않았을 것이다.

## 에세이 질문과 답변

**질문:** 온라인으로만 보던 사람들을 처음 교실에서 만났는데 "자주 만난 사람처럼 익숙했다"고 적으셨습니다. 맡은 범위가 넓어진 날, 옆에서 시민님과 정목님이 가르쳐 준 순간은 GitHub 코멘트로 주고받을 때와 무엇이 달랐나요? 28년 동안 신규사업을 기획하고 스토리위즈를 경영하며 사람을 모아 일해 온 경험에 비추어, 온라인으로 먼저 쌓은 신뢰가 오프라인에서 어떻게 작동했다고 보시나요?

**답변:** 그때는 내가 말로 설명하거나 타이핑을 했는데, 이제 가까이서 같은 화면을 보고 서로 알려 줄 수 있어서 능률이 한층 더 올랐다.

## 클로의 피드백

**좋은 점**
- 기술 답변이 PR 규칙을 "절차"가 아니라 "덮어쓰기를 막는 장치"로 짚었다. 실제로 이번에 캡틴이 PR 5개(#185~#189)를 통합 PR #198로 정리하고 머지 순서(#198 → #191)를 정한 장면과 정확히 맞닿는다. 누군가 순서를 잡지 않았다면 늦게 온 변경이 앞의 개선을 지웠을 것이다.
- 에세이 답변이 "말로 설명하던 것"과 "같은 화면을 보는 것"의 차이를 구체적으로 짚었다. 온라인에서 이미 서로를 알고 있었기에 오프라인에서 곧바로 같은 화면 앞에 앉을 수 있었다는, 인상적인 장면과 새롭게 알게 된 점을 잇는 흐름이 자연스럽다.

**개선점**
- 기술 답변에 오늘 직접 겪은 장면 하나를 붙이면 더 단단해진다. 예를 들어 "#186과 서버 PR이 약속을 다르게 알고 있었는데, PR 리뷰 단계였기에 합치기 전에 네 군데를 잡을 수 있었다"처럼. `[PR 규칙의 실제 사례 한 줄 — 다음 기회에]`
- 에세이 질문의 뒷부분(28년 경력에서 온라인으로 쌓은 신뢰가 오프라인에서 어떻게 작동했는지)은 답이 비어 있다. 스토리위즈를 경영하며 원격으로 먼저 만난 파트너를 처음 대면했던 기억이 있다면 한 문장 덧붙여 보시면 좋겠다. `[경력과의 연결 한 문장 — 다음 기회에]`
- opencode·open design 연결은 "아직 못 풂"으로 정직하게 남겼다. 집에서 다시 해 볼 때 어디서 막혔는지(설치, 연결 설정, 오류 메시지)를 한 줄 적어 두면 다음 일지의 좋은 재료가 된다. `[막힌 지점 기록 — 다음 기회에]`
